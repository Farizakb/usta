# LiteLLM's second hijack dominates October's Python threats

The incident that matters most for a Python LLM-app stack in the 2026-09-23 to 2026-10-23 window is the **2026-10-21 compromise of litellm 1.107.0**: malicious wheels and official Docker images carried a `.pth`-based credential stealer plus an hourly remote-code loader, live for roughly 3 hours with an estimated 49,000+ downloads. The safe version is **1.106.2**. Anyone who installed or pulled 1.107.0 must treat the host or container as compromised and rotate everything it could reach. The same token-theft pattern shows up in the GhostAction GitHub Actions campaign (Oct 7-12, counts from hundreds to 30,000+ repos depending on source) and in worm seeding (Tensorlake npm on Oct 8, "testmetest" Oct 19-22), which now includes "hostage token" wipers that change the order of incident response. Patch-class items are lower drama but concrete: **mcp (Python SDK) < 1.30.0 / < 2.2.0** has an OAuth issuer-validation flaw, **CPython 3.14.8** (Sep 30), **Django 6.1.2/6.0.9/5.2.18** (Oct 6), OpenSSL's 14-advisory batch (Sep 29), and PgBouncer 1.26.1 (auth bypass, Oct 14). Evidence is thinner than it looks: much of it is vendor blogs and search-summary secondary sources, several primary pages were never read, and the researchers found nothing dated Sep 23-Oct 4 in supply chain, which may be a search gap rather than a quiet period. Confidence ratings below reflect this.

## The LiteLLM 1.107.0 compromise is the incident to act on

**What happened.** Malicious litellm 1.107.0 (all seven wheels) hit PyPI at 11:39 UTC on Oct 21; Chainguard's scanner flagged it 16 minutes later and PyPI quarantined it ([Chainguard](https://www.chainguard.dev/unchained/litellm-attacked-again-malicious-1-107-0-wheels-on-pypi-and-docker-hub-october-2026)). Docker images for v1.107.0 carried the same payload (ghcr.io/berriai/litellm, litellm-database, litellm-non_root, docker.io/litellm/litellm); Chainguard also lists the `latest`, `main-latest` and `main-stable` Docker Hub tags as affected, while SecurityWeek says tags were removed or repointed to clean artifacts ([SecurityWeek](https://www.securityweek.com/litellm-compromised-in-fresh-supply-chain-attack/)). Clean versions: 1.106.2, plus 1.107.0rc1/rc2.

**Why source review would not have caught it.** The sdist's `pyproject.toml` gained one build line so maturin copied a `cook/` folder into site-packages root; `cook.pth` imports `cook.py`, so the payload runs on **any Python start in that environment, even if litellm is never imported**. The GitHub tag and sdist lack the payload (wheel-only trojan) ([Chainguard](https://www.chainguard.dev/unchained/litellm-attacked-again-malicious-1-107-0-wheels-on-pypi-and-docker-hub-october-2026)). The ~61 KB stealer harvests SSH/GPG/TLS keys, shell history, browser data, AWS/Azure/GCP and Kubernetes credentials, CI/CD secrets, configs of 15+ AI coding tools, env vars, IMDS data, and the LiteLLM proxy credential tables via `DATABASE_URL`. It exfiltrates over plain HTTP to a look-alike domain, and a detached daemon (Linux/macOS) polls a GitHub dead drop hourly and executes whatever Python it finds, with no integrity check. On Windows the loader fails but the stealer runs. The dead drop was empty during Chainguard's analysis, so second-stage execution was not observed. Wiz saw stolen AWS credentials abused about 4.5 hours after exfiltration, including Amazon Bedrock queries ([SecurityWeek](https://www.securityweek.com/litellm-compromised-in-fresh-supply-chain-attack/)).

**Indicators.** Domain `www.litellm[.]dev` (not litellm.ai); files `cook.pth`, `cook.py`, `sitecustomize.py` in site-packages root; `/tmp/.pc_once_*`, `/tmp/remote_code_loader.lock`; env `PRIVCOLLECT_ACTIVE=1`; second-stage requests to `/codepy` (a hit there means possible arbitrary code execution). Full wheel hashes and image digests are in the Chainguard post.

**How the attackers got in is disputed (conflicting accounts).** SecurityWeek, citing LiteLLM's investigation, says attackers obtained GitHub CLI OAuth tokens from an internet-exposed internal deployment, and LiteLLM suspects Claude Code embedded tokens in response bodies that were then logged. With three developers' credentials they disabled branch protections, redirected the releaser to a lookalike repository and published signed artifacts ([SecurityWeek](https://www.securityweek.com/litellm-compromised-in-fresh-supply-chain-attack/)). Aviatrix's vendor blog describes it as one account triggering the releaser workflow and a second approving it, defeating four-eyes review, and itself calls the token-theft mechanism speculation ([Aviatrix](https://aviatrix.ai/threat-research-center/litellm-compromised-supply-chain-attack-credential-stealer-backdoor/)). Chainguard says the access path is unexplained and not linked to the March 2026 TeamPCP compromise of litellm 1.82.7/1.82.8 (stolen PyPI token, `.pth` payload, ~3h live) ([CSO Online](https://www.csoonline.com/article/4206245)). Treat the root cause as unconfirmed. No PyPI, PSF or BerriAI primary advisory was fetched; confidence is **high** that 1.107.0 was malicious (several independent vendors), **medium** on the intrusion path. One transferable lesson holds regardless: if your app logs LLM or tool responses, those logs can contain tokens.

## Token theft in CI is the shared root cause across the window

**GhostAction (Oct 7-12).** Maintainer accounts (Takashi Kitao, Henry Wu) were used to push "Security Audit" workflows (`security-audit.yml`, `github_actions_security.yml`) straight to default branches without PRs; the payload scans 13 credential patterns across full git history and exfiltrates over plain HTTP to **193.32.204[.]199**. GitHub began blocking the workflow on Oct 9. This is not a GitHub Actions vulnerability; the likely entry is leaked PATs from infostealer logs (inference). Confirmed exfiltration from uber/athenadriver ([DIESEC](https://diesec.com/2026/10/ghostaction-github-actions-attack-steals-secrets/); [Aviatrix](https://aviatrix.ai/threat-research-center/ghostaction-github-actions-credential-theft-2026/)). **Figures conflict because they measure different things:** the first wave was 345 repos; GitGuardian later reported ~1,900 accounts, 30,000+ repos targeted and 3,174 secrets targeted (not confirmed stolen); another figure is 2,577 secrets for Aug 31-Sep 30; Aviatrix says 3,325+ and lists PyPI, Anthropic and OpenAI keys among them ([SC World](https://www.scworld.com/brief/ghostaction-campaign-escalates-targeting-over-30000-github-repositories); [StepSecurity](https://www.stepsecurity.io/blog/ghostaction-returns)). The campaign start is also uncertain (Sep 2025 vs "since August 2026"). Confidence: **high** the campaign occurred, **low** on scale. Primary reports (THN, Socket, GitGuardian) were not read directly.

**Worm seeding.** `tensorlake@0.5.144` (npm, Oct 8) was flagged by Socket 11 minutes after publication and removed about 3 hours later; it belongs to the ChainDrop/Shai-Hulud family, and no PyPI tensorlake compromise was found ([Socket](https://www.socket.dev/blog/tensorlake-compromise)). Its `gh-token-monitor` persistence runs a home-directory wipe if the stolen GitHub token is revoked. The "testmetest" Miasma-variant test (15 npm packages, Oct 19-22, operator-owned accounts only, no third-party victims yet) can republish to **npm, PyPI, RubyGems and JFrog**, runs via `binding.gyp`, tries to disable StepSecurity Harden-Runner, and has a Python component (`sync.py`, hourly) plus a 48-hour token-polling wiper ([SafeDep](https://safedep.io/testmetest-npm-worm-miasma-variant/)). SafeDep has not confirmed lineage to Miasma. The practical consequence for responders: **remove persistence before revoking tokens**, or the wipers trigger.

**Smaller items.** Xygeni logged 7 malicious PyPI versions Oct 18-21, including `leakdeep 3.0.0` and `pyyi 2.5.0-2.5.5` (five versions in 22 minutes from a repeat offender), with no behavioral detail ([Xygeni](https://xygeni.io/blog/xygeni-malicious-code-digest-93/)). OVHcloud CLI release assets were reportedly replaced with malicious binaries (reported Oct 19; a single DEV Community snippet, **low confidence**) ([DEV Community](https://dev.to/anoymask/ovhcloud-cli-supply-chain-attack-release-assets-replaced-to-steal-developer-secrets-2d2i)).

## What to do this week, in priority order

**1. Establish LiteLLM exposure (today).** Search lockfiles, image digests, build logs and CI caches for litellm 1.107.0 and the affected image tags, using shell tools only, not `python` or `pip` inside a suspect environment. If hit: isolate; kill the detached loader first, then remove `cook.pth`, `cook.py`, `sitecustomize.py`, `__pycache__` and `/tmp` markers; block egress to litellm.dev and the dead drop; check proxy logs for `/codepy`. Then rotate SSH/GPG/TLS keys, cloud and Kubernetes credentials, SCM and publish tokens, AI-tool tokens, `DATABASE_URL`, LiteLLM master and virtual keys, and every provider key in the credentials table, and review cloud audit logs including Bedrock/OpenAI usage. Rebuild from verified artifacts, pin `litellm==1.106.2`, and pin images by digest ([Chainguard](https://www.chainguard.dev/unchained/litellm-attacked-again-malicious-1-107-0-wheels-on-pypi-and-docker-hub-october-2026)).

**2. Scan all environments for the other payloads.** In every venv, container and CI runner image, look for unexpected `*.pth` files and `sitecustomize.py` (a stdlib one-liner over `site.getsitepackages()` works, run from an isolated interpreter with `-I`). In repos, grep `.github/workflows` for `security-audit.yml`, `github_actions_security.yml` and the IP 193.32.204.199. If any machine ran the Tensorlake or testmetest packages, disable `gh-token-monitor` (systemd user unit, LaunchAgent or scheduled task) and delete its config before revoking GitHub tokens ([Socket](https://www.socket.dev/blog/tensorlake-compromise)).

**3. Patch the in-window CVEs.** Upgrade `mcp` to 1.30.0 or 2.2.0 if you use its OAuth client or connect to third-party MCP servers; CPython to 3.14.8 in base images (Fedora took about two weeks, so check distro lag; 3.10-3.13 users need the matching patch release, version unconfirmed); Django to 6.1.2/6.0.9/5.2.18; PgBouncer to 1.26.1; OpenSSL to the fixed build for your branch; and Starlette beyond the BadHost fix. Use `uv pip list`, `pip-audit` and `osv-scanner` against lockfiles to confirm; `pip show starlette` covers the transitive FastAPI pin.

**4. Turn on a dependency cooldown.** Every 2026 AI-library malware release was pulled within hours (LiteLLM ~3h, Guardrails AI 0.10.1 ~2h, mistralai 2.4.6 within hours), so a 7-day cooldown would have avoided all of them. In uv: `[tool.uv] exclude-newer = "7 days"` plus `exclude-newer-package` overrides; pip has `--uploaded-prior-to` (26.0) with relative durations (26.1); Poetry 2.4.0 has `solver.min-release-age`; align Renovate `minimumReleaseAge` with uv. These syntaxes come from secondary summaries, so check each tool's docs; private indexes without upload dates need `exclude-newer = false` on that index ([pydevtools](https://pydevtools.com/handbook/explanation/what-is-a-dependency-cooldown/); [Nesbitt](https://nesbitt.io/2026/03/04/package-managers-need-to-cool-down)). A cooldown does not detect malware or cover sdist build-time code, and the Dependabot setting that lets security patches through immediately is worth keeping.

**5. Install from hash-pinned lockfiles only.** Use `uv.lock` or `uv export` plus `pip install --require-hashes` in CI and Docker builds, and verify the installed wheel, not just source. This is the control that stops a version from floating to 1.107.0.

**6. Lock down CI and tokens.** Replace PATs with fine-grained, short-lived tokens or OIDC; enable secret scanning and push protection (GitHub native, gitleaks, trufflehog; tool names are general knowledge, not sourced in the research); SHA-pin all Actions; set minimal `permissions:` on `GITHUB_TOKEN`; protect `.github/workflows` with branch protection or CODEOWNERS; require approval for workflow runs; allowlist runner egress and block plain HTTP. Never expose secrets to `pull_request_target` or public-PR workflows, which is the "Comment and Control" vector against coding agents running in Actions ([Vaughan roundup](https://codex.danielvaughan.com/2026/05/02/spring-2026-ai-coding-agent-vulnerabilities-cursor-rce-comment-control-codex-cli-defence/), secondary).

**7. Close exposed LLM endpoints.** Audit that LiteLLM, Ollama and vLLM listeners are not internet-reachable, sit behind authentication, and have per-key budgets and rate limits; alert on spend anomalies. This answers the LLMjacking trend that Symantec's honeypot captured and an earlier Sysdig report of a misconfigured Ollama server used as an attack engine ([CSA note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/06/CSA_research_note_llmjacking_evolved_offensive_agentic_20260620-csa-styled.pdf)).

**8. Scrub secrets from logs and agent reach.** The LiteLLM investigators' leading theory involves tokens in logged response bodies, so redact `Authorization`, OAuth and API-key patterns from LLM and tool-call logs. Keep `~/.ssh`, cloud credential directories and `.env` outside what dev machines' coding agents can read; run agents in a devcontainer or VM with no long-lived credentials.

## Longer-term practices

**Treat the install as code execution.** `.pth` files and `sitecustomize.py` run at interpreter start, so "we never imported it" is no defense, and wheel-only trojans bypass source review. Build in an environment with no secrets, run CI jobs that install third-party code without cloud credentials, and use Trusted Publishing (OIDC, PEP 740 attestations) if you publish packages. Attestations prove provenance, not benignness: a compromised workflow still publishes valid-looking artifacts, as the PyTorch Lightning 2.6.2/2.6.3 incident (workflow-file malware, late April) and, per SecurityWeek, the LiteLLM redirected-releaser chain show. For maintainers, enforce multi-party release approval that cannot be satisfied by one compromised identity chain ([Sigstore](https://blog.sigstore.dev/pypi-attestations-ga/)). Adoption of attestations was about 5% of top projects at launch; no current figure was found.

**Design the LLM app for injection, not against it.** OWASP's LLM Top 10 (2025) remains the base list and the OWASP Top 10 for Agentic Applications 2026 (released 2025-12-09) covers tool-using agents; there is no complete prompt-injection fix ([OWASP GenAI](https://genai.owasp.org/llm-top-10/); [Cycode summary](https://cycode.com/blog/owasp-top-10-agentic-applications/)). The defensible posture, which is the researchers' synthesis rather than a single cited standard, is least privilege per tool, no ambient credentials in the agent process, human approval for irreversible or exfiltrating actions, model output treated as untrusted (parameterized SQL, no `eval` or `shell=True`, the same class as Semantic Kernel's CVE-2026-26030, fixed in semantic-kernel 1.39.4), generated code in a no-network, no-secret sandbox, egress allowlists, and full tool-call logging ([Microsoft](https://microsoft.com/en-us/security/blog/2026/05/07/prompts-become-shells-rce-vulnerabilities-ai-agent-frameworks/)). For MCP, the draft spec forbids token passthrough, requires issuer validation against mix-up attacks, exact `redirect_uri` matching and per-client consent for proxies, advises blocking private and link-local ranges including 169.254.169.254, and tells clients to show the exact command before installing a local server ([MCP security best practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)). Pin MCP servers by version; typosquatted and malicious MCP packages are a recurring pattern, such as three malicious PyPI MCP servers with reverse shells ([JFrog](https://research.jfrog.com/post/3-malicious-mcps-pypi-reverse-shell/)).

**Model artifacts and gateways.** Prefer safetensors. `torch.load` defaults to `weights_only=True` since PyTorch 2.6, but a `weights_only` unpickler flaw (CVE-2026-24747, CVSS 8.8) was fixed only in 2.10.0, and picklescan bypasses exist, so do not rely on scanners ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-24747); [OSV](https://osv.dev/vulnerability/PYSEC-2026-2873)). Because LiteLLM was hit twice in 2026 and carries a long CVE tail (SQLi in key validation, MCP-endpoint command injection, reportedly in CISA KEV), decide deliberately whether a gateway holding all provider keys belongs in your trust boundary, or isolate it with per-service keys and a private network. The LiteLLM CVE details are secondary-source and unverified ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2026-30623); [CSA](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/06/CSA_research_note_LiteLLM_RCE_CVE-2026-42271_20260609-csa-styled.pdf)).

**Regulatory carry-over, only if your employer ships into the EU.** EU CRA vulnerability-reporting duties for manufacturers started 2026-09-11 (24h early warning, 72h notification), with open-source steward duties from 2027-12-11; AI Act high-risk obligations are being delayed by the Digital Omnibus, whose formal adoption is unconfirmed; NIST SSDF 1.2 was still a draft in the sources found ([HeroDevs](https://www.herodevs.com/eu-cyber-resilience-acts); [Gibson Dunn](https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines-and-other-key-changes/)). The practical carry-over is SBOMs and a vulnerability-handling path.

## Background versus in-window, and where coverage stops

**In-window events (confirmed dated):** LiteLLM 1.107.0 (Oct 21); GhostAction (Oct 7-12); Tensorlake npm (Oct 8); testmetest worm test (Oct 19-22); small PyPI malware uploads (Oct 18-21); OVHcloud CLI (Oct 19, low confidence); MCP SDK WS-2026-0089 (Sep 28); GitLab Duo CVE (Oct 12); Symantec honeypot report (Oct 21); CPython 3.14.8 (Sep 30); Django (Oct 6); OpenSSL (Sep 29); PgBouncer/psqlODBC/JDBC (Oct 9-14); KEV additions listed above.

**Background, outside the window, included for context:** Starlette BadHost (KEV Sep 2); LiteLLM March compromise and 2026 CVEs; Guardrails AI 0.10.1 (CVE-2026-45758, May 11, fixed 0.10.2); mistralai 2.4.6 (May 12); Semantic Kernel CVEs (May 7); Context7 MCP CVE-2026-75130 (Aug 18); Mini Shai-Hulud/Miasma/Hades PyPI waves (June); ChainDrop/keyv (Aug 4); `openaii` PyPI `.pth` malware (Sep 11); Klue breach (June); Cursor DuneSlide CVE-2026-50548/-50549 (disclosure date conflicts: April 2 vs July 1). A GBHackers page bannered 2026-10-18 is a July 2025 article on mcp-remote CVE-2025-6514; ignore it as a new disclosure.

**Coverage gaps the researchers reported.**
- Supply chain: nothing found dated Sep 23-Oct 4; no PyPI, PSF or GitHub statement on any incident; no in-window slopsquatting or AI-library typosquat campaign; GhostAction, Tensorlake and testmetest primary reports only partly read; several fetches (The Hacker News, The New Stack) returned 403.
- AI frameworks: no in-window CVEs found for LangChain, LlamaIndex, vLLM, Ollama, Ray, MLflow or transformers; no Cursor, Codex or Claude Code CVEs; no Hugging Face pickle incident; no provider breach. Researchers flagged this may be a search-tool limit, so check the GitHub Advisory Database and OSV.dev directly. Aggregator figures such as "30 CVEs in 60 days" and "5,832 of 9,695 MCP servers vulnerable" are unverified and were excluded.
- Backend: no in-window advisories found for Flask/Werkzeug, urllib3, requests, httpx, aiohttp, Pydantic, SQLAlchemy, Celery, Jinja2, cryptography, PyYAML, Pillow, uvicorn or gunicorn, based on a single broad search; Redis, RabbitMQ, Nginx, the Linux kernel, Docker/containerd/runc, Kubernetes and cloud bulletins were not researched. CVSS scores were mostly unavailable for CPython, Django and OpenSSL. WebFetch output was model-summarised, so confirm critical CVE IDs against NVD before quoting them.
- Guidance: pip-audit, osv-scanner, Sigstore, SLSA, Scorecard and secret-scanning tooling had no primary sources; Python tool names in the checklist are the author's general knowledge. No vendor-primary guidance on coding-agent permission models was fetched.
- Single-source items to treat cautiously: GitLab Duo CVE, OVHcloud CLI, the PyPI phishing/num2words item, the third-party Postgres open issues (SCRAM enumeration, RLS cache), and the LiteLLM CVE chain.

## Conclusion

October's lesson is that the Python-specific risk has moved from vulnerable code to **trusted-publisher identity**: LiteLLM was compromised twice in 2026 through the people and pipelines that publish it, and the artifact that did the damage existed only as a wheel. CVE scanning would have caught none of the malware cases, which is why the high-leverage controls are cooldowns, hash pins, short-lived tokens and CI egress limits rather than scanner coverage.

The second implication is operational. Worm payloads with dead-man wipers mean incident response now has a required order (remove persistence, then revoke, then rotate), and AI engineers add a failure mode that classic backend teams lack: LLM gateways concentrate every provider key in one process whose logs may leak tokens. Revisit the research after checking the primary advisories listed under gaps, especially the PyPI and BerriAI statements on 1.107.0, since the root cause and the true blast radius are still unsettled.
